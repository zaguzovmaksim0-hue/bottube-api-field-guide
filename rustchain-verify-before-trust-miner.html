RustChain Miner: A Verify-Before-Trust Dry-Run Tutorial

Practical field note · September 2026

If you are testing RustChain on unfamiliar hardware, the safest first goal is not “start mining.” It is to prove what code you are running, what hardware the miner sees, what the fingerprint checks report, and whether the public node is reachable — without changing network state. RustChain's current Linux miner supports a dry-run path that makes this possible.

What this tutorial does: inspect the repository, identify the runtime, run a local fingerprint/dry-run check, read the output, and verify the public health endpoint. It deliberately stops before attestation, enrollment, or the mining loop.

1. Start from the canonical repository

The public source is Scottcjn/Rustchain. Clone it, record the exact commit, and inspect the miner path before running anything:

git clone https://github.com/Scottcjn/Rustchain.git
cd Rustchain
git rev-parse HEAD
sed -n '1,180p' miners/linux/rustchain_linux_miner.py

Recording the commit matters because a test result without a source revision is hard to reproduce later. If behavior changes, the commit lets you tell whether the hardware changed or the code did.

2. Record the environment before installing or changing packages

uname -a
python --version
uname -m
command -v python

On my physical Android/Termux test device the relevant architecture was aarch64. The miner reported a Cortex-A520 CPU, eight logical cores, and about 11 GB of visible memory. That is useful evidence, but it is not the same thing as a reward multiplier: fingerprint success and reward weight are separate questions.

Android caveat: the Linux miner currently warns that Android is not a primary supported Linux-miner platform and that some hardware probes can be incomplete. Treat that warning as evidence, not as something to suppress.

3. Use dry-run before any state-changing operation

From the repository root, use the miner's dry-run mode with your own wallet identifier:

python miners/linux/rustchain_linux_miner.py \
  --wallet YOUR_RTC_WALLET \
  --dry-run

The current dry-run explicitly says that it will not modify mining/network state. It performs local platform/fingerprint work and a read-only health check, then tells you what the next real stages would be rather than executing them.

A healthy dry-run should give you enough information to answer these questions:

  • Which CPU and architecture did the miner detect?
  • How many fingerprint checks are available on this platform?
  • Did the complete fingerprint bundle pass?
  • Did the public node health probe return successfully?
  • Is the wallet shown in the output the wallet you intended to use?

4. Read the fingerprint result as a bundle

On the Android/Termux run I captured, the current base suite exposed six checks:

CheckWhat it contributes conceptually
Clock-skew / oscillator driftTiming behavior
Cache timingMemory/cache behavior
SIMD identityInstruction-unit behavior
Thermal driftPhysical timing under changing conditions
Instruction-path jitterExecution timing variability
Anti-emulationIndependent VM/emulator/runtime clues

All six passed in native Termux on the physical phone. In a separate friendly red-team run on the same phone inside Debian PRoot, the first five passed but anti-emulation failed because systemd-detect-virt reported proot. That contrast is a good illustration of why RustChain uses a bundle: a single timing probe does not have to carry the entire decision.

5. Verify the node health separately

The public production hostname used by current miner configuration is https://rustchain.org. A bounded read-only health check is:

curl --fail --silent --show-error \
  --connect-timeout 5 --max-time 15 \
  https://rustchain.org/health

Do not “solve” a certificate failure by reflexively adding -k or disabling TLS verification. A network-path or certificate error is information. For production automation, fail closed and investigate the trust path rather than silently downgrading it.

6. Keep hardware identity separate from wallet identity

This distinction caught a real bug in my own test workflow. The hardware-derived miner identity on one run was not the same as the RTC wallet that actually held a balance. A balance check against the hardware ID returned zero while the wallet itself held funds. The practical rule is simple: when displaying wallet funds, query the wallet identifier, not a hardware/miner label unless the API explicitly defines them as the same identity.

Before moving beyond dry-run, write down:

source commit
node URL
wallet address / miner_id used for payout
CPU + architecture
fingerprint result
health result

That small evidence packet makes later attestation or reward debugging much easier.

7. What comes after dry-run?

The miner describes the real sequence as attest → enroll → mining loop. Those stages are state-changing and should be a separate decision. If your goal is compatibility testing, QA, documentation, or a bounty that only asks for a dry-run, stop here. There is no engineering benefit in turning a read-only test into a persistent miner merely because the binary can do so.

8. A reproducible troubleshooting order

  1. Pin the repository commit.
  2. Record OS, architecture, Python/runtime versions.
  3. Run the local dry-run/fingerprint path.
  4. Read every failed check and its raw evidence.
  5. Probe /health separately with bounded TLS-verified HTTP.
  6. Verify the wallet identity used for balance/payout operations.
  7. Only then decide whether a state-changing attestation/enrollment is actually required.

This order is deliberately boring. That is the point. It separates source, local hardware, network transport, identity, and reward accounting so one failure does not get “fixed” by randomly changing all five layers.
